- (constraint) The PRD requires one active assignment per driver, at most one assigned driver per trip, retry-safe money movement and independent trip and payment states. Clients recover authoritative trip state after reconnecting.
- (assumption) Use a modular monolith as the working deployment model for discussion. Team size, stack, hosting and independent release needs are unconfirmed. Revisit before selecting a starter or deployment topology.
- (decision) AD-1 [ADOPTED] — Dispatch owns assignment. For a new acceptance, validate the offer, searching trip and eligible, available driver and claim the trip and driver in one backend transaction. The first valid commit wins, independent of phone timestamps. Enforce at most one active assignment on either side. Replaying a successful acceptance returns its recorded assignment, even after the offer expires. A competing driver gets Trip taken and their own availability stays unchanged. Binds R03–R05 and Stories 2.4–2.5. Prevents double assignment and contradictory retry responses.
- (decision) AD-2 [ADOPTED] — Trip completion and fare capture. For a payable trip, commit Completed and one durable capture request in the same local transaction. A payments worker delivers that request using a stable payment operation key. After an unknown provider response, keep payment pending and reconcile the original operation before any further charge attempt. Delivery retries and repeated callbacks must not create additional charges or ledger entries. A confirmed failure leaves a recoverable balance and preserves Completed. Binds R07, Stories 3.7 and 4.2, and the rider receipt and operations timeline. Prevents a lost capture after completion and duplicate charges after a lost response.
- (decision) AD-3 [ADOPTED] — Version-checked trip actions. Each trip-state command carries a unique request ID and the server-owned trip version observed by the caller. Within the authorized trip and actor scope, recognize a replay of the same command before checking the version and return its recorded outcome. For a new command, validate the expected version and allowed transition, and commit the state change, version increment and command outcome atomically. A stale command has no side effects. Refresh the current trip before requesting fresh intent. A delayed cancellation after pickup cannot cancel the trip or assess a fee. Binds R02, R05, R06, the trip lifecycle and reconnect behavior. Prevents stale writes and duplicate transitions.
- (decision) AD-4 [ADOPTED] — Track driver location independently of trip actions. Within the active assignment, a newer location sample may advance the displayed position. Late or duplicate samples cannot replace a newer sample or refresh its age. GPS updates leave the trip version unchanged. When the latest sample is older than 30 seconds, mark location stale and display its last-update time. Starting or cancelling a trip still advances the trip version under AD-3. Binds R05 and Story 3.2. Prevents telemetry from rejecting valid trip actions or making stale positions look current.
- (decision) AD-5 [ADOPTED] — Pilot deployment model. Rider, driver and operations clients call one modular backend backed by one transactional database. Run the API and background worker as independently runnable processes from the same codebase. The API handles interactive requests and the worker handles durable payment capture and reconciliation. This supersedes the provisional deployment assumption, preserves local atomicity for AD-1 and AD-2, and lets outstanding capture work survive a worker restart. Language, framework and hosting remain open.
